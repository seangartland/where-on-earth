# Zoom diagnosis and replacement design

Date: 2026-11-21. Scope: design only; no implementation or deployment. Evidence: the supplied `BRIEF-zoom-astra.md` and this checkout. Routing: direct diagnosis in the assigned Codex design lane; implementation belongs to a later build lane.

## Decision

The structural problem is that detail is a disposable camera-window loading job, rather than a resident geographic asset: gestures can invalidate work, bundles delay the first useful bytes, absent tiles introduce parent dependencies, and compressed-byte prefetch still leaves decode, upload, and presentation on the interaction path. The evidence does **not** establish how many milliseconds each contributes on the owner's iPhone. It establishes expensive request amplification and an architecture capable of repeated cold work; cutting z10 alone demonstrably does not solve it.

Replace the default mosaic's window loader with immutable geographic image pages, a coverage manifest, and a bounded GPU page cache. Warm the current target's final z9 footprint at round start, including decode and upload, and render those same resident pixels at intermediate scales through mipmaps. For arbitrary exploration, request the final wanted pages directly and retain intersecting pages across camera changes; never require a sequence of completed intermediate windows. Keep the globe, camera, home position, base image, satellite styling and inset compositing. z10 remains an optional enhancement after z9 readiness, not a readiness dependency.

This is a testable design for MapTap-class *prepared-target* interaction, not a claim that cold, arbitrary geography can appear instantly over a slow connection. Known-target anticipation and general exploration need separate scorecards. The main tradeoff is speculative bandwidth and GPU memory for eliminating work at gesture time.

## 1. What the implementation actually does

References below use repo-relative paths and function names as durable anchors; line numbers refer to this checkout.

- `src/globe/surface.js:535–638`: default own mosaic, ladder `[5,7,8,9,10]`, provider routing and z10 pilot check. z7 is described as full coverage; z9 is **not** full coverage, despite the Daily-prefetch comment. Brief evidence supplies z9 holes. Keep EOX's existing opt-in compatibility path; the replacement uses only our mosaic.
- `sampleInsetView`, `insetWindowAt`, `pickInsetWindow` (`surface.js:831–903`): 81 screen rays plus the center bound a Mercator footprint; desired resolution considers `targetDist`, but footprint geometry uses the current camera. A future deeper resolution can therefore fail to fit the current wide footprint and fall to a shallower rung. The picker can jump straight to z9; there is no unconditional z5→z7→z8→z9 completion barrier.
- `insetWindowAt:859` removes margin only at `satProvider.maxZ`, not `effectiveMaxZ()` or the deepest covered rung. Thus z9 still has a one-tile margin outside pilots and under `?zcap=9`. A 6×6 visible footprint becomes 8×8 rather than 36 cells. This is an amplification mechanism, not a claim that all those cells were fetched in the supplied probe.
- `startInsetWindow:911–962`: two render targets; clear/repopulate one, abort unrelated requests, cancel speculative jobs and bundles. Completed compressed blobs survive in the LRU, but prior decoded images do not. Old image coverage can remain visible underneath; this is not a total blank on every transition.
- `prepareInsetPrefetch:1241`: idle next-rung warming starts at half-visible completion, or via explicit zoom prioritization. It is still competing with visible jobs and tied to the current window. The comment says focal 3×3; prioritized code actually uses `visibleTileCoordinates(arriving)`, the whole arriving visible rectangle (`src/globe/inset-footprint.js`). Ordinary warming can expand every current cell into descendants. Speculative keys use `win.providerId`, whereas visible keys use the resolved provider; pilot warming can consequently miss cache-key reuse.
- `prefetchDailyTiles:1326`: up to 5×3×9 = 135 individual jobs before deduplication, current location first, ascending z7/z8/z9. Starts via idle callback (5,000 ms timeout) or 1,000 ms timeout, three active jobs, compressed blobs only. Pointer down/wheel call `pauseDailyPrefetch` in `src/globe/pin.js`; completion of a visible window calls resume. Pausing stops new dispatch, not already active requests. It is not a general all-mode round-start loader and does not ensure a full deep viewport.
- `requestInsetBundle:1033`, `src/globe/tile-bundle.js`, `tile-bundle-worker/src/index.js`: visible uncached sources are submitted as a JSON POST. The worker dynamically assembles the exact requested set, with a sorted-set cache key. This is not a prebuilt window lookup that simply misses for nonstandard rectangles. Browser validation requires an exact returned key set. Client grouping excludes default z10 and pilot keys, even though the worker already lists the pilot provider. Margins remain separate tile requests.
- Bundle assembly awaits all origin bodies before returning WOE1; browser awaits the entire `arrayBuffer()` before decoding any member. One source failure rejects `Promise.all`; that await is outside the worker's local `try`, so the handler rejects rather than taking the intended `bundle failed` branch. Client failure then clears bundle reservations and falls back to individual visible requests. There is no explicit bundle deadline. POST is not cached by `sw.js`; unpacked members only enter the in-memory LRU, not SW storage. A successful aggregate request reduces browser fan-out but does not eliminate worker subrequests on a worker-cache miss.
- `fetchInsetTile`, `loadInsetTile`: 404 adds a session negative-cache entry and walks to ancestors; the walk decrements integer zooms and can include z6, although the visible ladder omits it. A “ready” window can contain ancestor pixels or exhausted tiles. Ready is not equivalent to native z9 sharpness. 429 or five consecutive errors trip 60–480 second pauses; 404 does not trip that breaker.
- `decodeInsetTile`, `pumpInsetUploads`, `finishInsetTile`: `createImageBitmap`, optional canvas ancestor crop and another bitmap creation, queued texture copies, bitmap disposal. Fade starts at one-third visible coverage; readiness waits for all visible cells to resolve, and mip generation waits for all cells including margins.
- `initImagery:1913`, `ensureInsets:760`: typical portrait buffers are 2048×4096 **each**. Two RGBA8 level-zero buffers occupy 64 MiB; full mip chains increase that to about 85.3 MiB, excluding base image, framebuffer, browser overhead and temporary bitmaps. Small-device fallback is two 1536-square buffers. This memory is fixed by capability/orientation, not proportional to useful loaded cells.

The correct latency equation is a dependency graph: for each visible pixel, dispatch gate + required source-chain network completion + decode + upload + first display, then take the last required pixel and any remaining fade. Network, camera easing, upload and fade overlap. Summing every row would manufacture a false explanation.

An **ESTIMATED illustration**, not a fit to the supplied evidence: three successive 0.4–0.8 s window/body completion episodes consume 1.2–2.4 s; a failed bundle followed by a 0.4 s individual/ancestor dependency adds another tail; 0.1–0.3 s of upload/presentation can make the experience several seconds. Conversely a direct cache hit can be far faster. Only the trace specified below can prove which episode dominates the phone. The supplied data cannot legitimately produce a measured millisecond attribution pie chart.

## 3. MapTap: ranked, falsifiable explanations

Ground truth is the brief's same-browser comparison: satellite detail appeared sharp and stable within the scroll batch, with no captured blurry phase. It supplies no network trace, resolution equivalence, cache state or GPU evidence. A read of the [public MapTap page](https://maptap.gg/) on this date exposed a game shell, not its renderer or transport; this design makes no implementation claim from that page.

Could instead be very fast reactive loading; no pre-gesture trace is supplied. | Fresh browser profile, record requests from navigation, wait 0/2/5/10 s before identical gestures, then repeat with network disabled immediately before zoom. These mechanisms can coexist. Hosted imagery or another engine is neither established nor required by the evidence. We should reproduce the property “final pixels ready before they are requested visually,” not copy an unverified stack.

## 4. Replacement architecture

### 4.1 Assets: immutable 4×4 geographic pages

Use fixed, globally aligned blocks of 4×4 existing 256-pixel tiles, producing one 1024-square JPEG per page. Key: `/s2-pages/<content-version>/<z>/<pageX>/<pageY>.jpg`; pageX=floor(wrappedTileX/4), pageY=floor(tileY/4). Publish pages for z5, z7 and z9; omit z8 from the new runtime ladder. z9 supplies actual final useful detail; z7 supplies broad context; z5 bridges the base to context. The render resolution is independent of the resolution being fetched. No new mosaic acquisition, z10 expansion, paid CDN feature or external imagery.

Build pages offline from existing own-mosaic tiles, with missing z9 cells deterministically filled from the deepest available **approved** ancestor among z8, z7, z5 and the own base. Do not introduce z6 artifacts. Record each cell's actual source z; a composed page is display-complete but does not pretend its fallback is native z9. Ocean outside detailed coverage is explicitly terminal base/ancestor coverage, not an endless request. Publish z10 pilot pages separately only when all page cells can be resolved using pilot or own z9 fallback; the manifest identifies which cells actually improve to z10.

JPEG encode at quality 90 initially; compare to the original tile composite before rollout. JPEG output is opaque, and missing cells are filled, so no alpha mask is needed. Adjacent page sampling needs a two-pixel replicated-neighbor gutter on all sides: encode 1028×1028, map only the central 1024 pixels to the page bounds, and clamp the texture. Generate the gutter from neighboring resolved mosaic pixels, including wrap. Avoid relying on independent mip chains at long-distance scale: page layers crossfade to the broader level once page texels project below 0.5 device pixel. Validate seams at all permitted scales; if gutter/mip seams fail, block release rather than silently increase blur.

Manifest, shipped as versioned app data, indexes existence, URL, byte length, content hash, cell source levels, dimensions and geographic bounds. Use a compact per-z page index and per-page 16-cell source map, not millions of individual JSON tile objects. Publish it only after all referenced assets are uploaded and verified. No request-time tile composition and no all-member bundle barrier. Plain GET pages reuse current SW host caching and normal CDN object keys. An initial page version is immutable; pixel or fallback changes require a new content version.

### 4.2 Residency and rendering

New `page-store.js` owns assets independently of camera generations: absent → queued → fetching → compressed → decoding → GPU-ready. Keep one promise per versioned page key, one compressed cache entry, one texture and last-use metadata. A camera change changes priority; it does not discard intersecting decoded data. Only cancel a fetch if it is neither visible nor pinned for the current round; finish nearly complete bodies when known transferred bytes exceed 75%.

Use a globe-attached geographic patch mesh for each resident page, over the existing sphere. This is the replacement inset implementation, not a flat map or a second engine. Generate Mercator-aligned sphere vertices with maximum angular cell size 0.5 degrees, shared exact boundary positions, and outward radius 1.0001. Render opaque page interiors, an outer two-texel edge feather, depth test on, depth write off, polygon offset where needed. Order layers base, z5, z7, z9, optional z10. Sample with existing no-color-conversion convention and the same satellite mix, limb darkening and ocean treatment as the present shader; move common satellite color math into a shared shader snippet. The base remains visible wherever no page is ready. Pins, outlines, picking and camera math stay unchanged. Mesh/texture construction and disposal are owned by the page store; no per-frame geometry recreation.

Pin the current target's selected z9 pages; draw them whenever their geographic region is visible, including intermediate zoom levels. Mips provide intermediate-scale images without fetching the intermediate ladder there. Broader pages still cover surrounding geography. Submit at most one page upload per frame, two decodes concurrently, prioritize visible pages over target-only pages, and use measured upload time to defer the next upload if the previous frame exceeded 20 ms. Do not evict a visible page for a speculative page. New cold pages fade for 100 ms when first introduced; already resident pages have no zoom-triggered fade. Switching off satellite retains the current target's compressed pages but releases GPU pages after 30 seconds hidden.

Budget textures at **64 MiB including mipmaps** and at most 12 allocated page textures (a 1028-square RGBA8 mip chain is about 5.38 MiB, so byte accounting usually limits residency to 11). Compressed in-memory budget is 8 MiB; SW retains its existing 100 MiB cap. The current visible set takes precedence, then current target, then context, then everything else by LRU. If visibility plus target exceeds budget, unpin the farthest target pages first. Do not secretly exceed the cap to satisfy an overly broad target footprint. Dispose textures, geometries and bitmap objects on eviction; retain no decoded bitmap after upload. Context restoration reuploads from compressed/SW data and reports preparation lost, without restarting a full ladder.

### 4.3 When and what to fetch

At `showRound()` immediately after `currentItem()`, call `prepareRoundImagery(item, roundToken)` once satellite initialization resolves. Validate finite lat/lng; never turn an unavailable coordinate into (0,0). The brief says targets are known in every mode, but `pvpBeginRound` describes a location payload without guaranteeing coordinates. Do not change PvP disclosure semantics: if its actual item has no coordinates, use visible exploration only and prepare at reveal when coordinates arrive. Test this explicitly.

For target preparation, compute the actual **maximum-zoom camera footprint** centered on the target using the same projection, viewport and minimum camera distance as the game, without moving the live camera. Use a scratch camera/globe transform and the existing footprint sampling math. Include one z9 tile of geographic safety margin for slight off-center zoom and pan. Convert the rectangle to fixed pages; sort center-containing page first, then distance to target. Select at most nine z9 pages and at most **3 MiB total advertised download bytes per round**, including any context or optional pilot bytes. If the complete footprint does not fit these caps, label preparation partial and preserve that fact in telemetry. Never report complete from central coverage alone.

Priority order: live visible missing pages; current target z9 pages; one target-containing z7 context page; other needed broad context for the visible camera. Target jobs start at round start, continue during input, and share a four-request pool with a maximum of two target-only requests. They are not paused merely because a finger is down. Visible requests can borrow all four slots. Deduplicate across all roles. Do not fetch z5/z7/z8 at the target before z9. Do not prefetch all five Daily targets: record their coordinates at load, prepare only the current round, and start the next target only when the round advances. This bounds abandonment waste. Any remaining byte budget does not authorize speculative future rounds.

For Save Data, disable speculative preparation; fetch visible z7 context and allow visible z9 only on the final-depth view. Missing z9 coverage uses the manifest's resolved fallback. The normal pathway uses z9 at final depth regardless of DPR; DPR does not demand nonexistent information above source quality. z10 pages, where present, are fetched only after z9 visible coverage is ready, while the final-depth pilot region is still in view and budget remains. A failed/missing z10 must never delay or demote z9. `?zcap=9` suppresses this optional enhancement.

For off-target exploration, compute desired resolution at most every 100 ms during motion, with a trailing final-input evaluation. Directly enqueue z9 when the target camera depth calls for it; do not first download z7/z8 to unlock it. Reuse resident page intersections as the camera crosses tile boundaries. Limit active visible request set to 12 nearest pages, with center first; beyond memory limits use broader resident coverage for the perimeter and report the gap. A page's physical boundaries, not camera-window boundaries, define cache identity. Cold arbitrary zoom still waits for network and decode, but it has one asset dependency, no failed bundle or parent-discovery chain.

## 5. Price and resource budget

All byte and labor figures in this section are **ESTIMATED**, not measured tile sizes. Use KiB/MiB for payloads; request counts from the brief remain measured. Budget assumptions: successful tile averages 20 KiB (sensitivity 10–40 KiB); page averages 320 KiB (16 tiles, conservative equal compression); headers, errors and WOE1 overhead excluded from illustrative payload totals. The asset build must publish actual bytes; abort speculative dispatch before the 3 MiB cap, never infer page size from these averages.

A 6-tile interval can intersect two or three four-tile pages per axis; this is why “one page per window” would be false. One-tile target margin turns 6×6 into 8×8, still two or three pages per axis. Tall viewports can exceed nine pages; they receive explicitly partial preparation. Shared pages reduce later costs; page quantization can increase a single zoom's bytes compared with the existing probe. The design is justified by latency only if the measured waste and mobile data gate pass.

Per-round speculative transfer: typical four z9 pages + one z7 page ≈1.56 MiB; nine z9 pages ≈2.81 MiB with context skipped if it would exceed 3 MiB. Hard speculative cap 3 MiB/round, ≤15 MiB across five played Daily rounds, typically ~7.8 MiB. Visible off-target exploration is additional and separately measured, not dishonestly hidden under this cap. A round abandoned without visiting warmed geography can waste the entire speculative amount. If only half the typical warmed bytes become visible, unused bytes are ~0.78 MiB/round. Cache reuse across revisits lowers transfer; it does not lower initial waste. Save Data speculative bandwidth is zero.

Traffic model: 10,000 DAU × five played rounds = 50,000 rounds/day; 100,000 DAU gives 500,000. Current 33–55 individual requests/round gives 1.65–2.75M and 16.5–27.5M browser tile requests/day respectively, **if** those probe paths are representative and cache-cold. Current Daily boot can add up to 135 requests/session, or 1.35M/13.5M daily at these populations before reuse; do not add that worst case to every deep zoom without tracing overlap. Bundle use lowers browser counts but can retain similar tile-origin fan-out.

At five pages/round the new path produces 250,000 / 2.5M page GETs/day, roughly 76 / 763 GiB of payload/day at 1.56 MiB/round. At ten pages/round: 500,000 / 5M GETs/day, bounded speculative bytes ~146 / 1,465 GiB/day at the 3 MiB cap. Off-target use, retries and manifest GETs are additional; app-cached manifest usually costs one per content version per user. Browser/SW hits remove requests before Cloudflare. For remaining page GETs with effective edge+Tiered origin-miss rate m, R2 reads = requests × m: at five pages/round and m=1–10%, 2,500–25,000 / 25,000–250,000 reads/day. These are scenarios, not claims about cache hit ratio or dollar pricing. Existing Tiered Cache remains on. Measure actual object hits and R2 operations to reconcile the model; no paid add-ons assumed.

Worst-case global page inventory at z5/z7/z9: 64 + 1,024 + 16,384 = 17,472 pages, ~5.33 GiB at 320 KiB/page, plus optional pilots and manifest. Omit pages consisting entirely of base-equivalent coverage, represented explicitly in the manifest. A full tile-input read upper bound is 16×17,472 = 279,552 member reads before dedup/cache, not per user. Use the existing mosaic/tile inventory on Pi bulk storage; cache raw inputs by version under `/mnt/external/woe-s2-pages/raw/<version>/`, derived scratch under `/mnt/external/woe-s2-pages/build/<version>/`. Never delete original satellite data. A repeat encode uses cached inputs; only changed content uploads. Emit input/cache-hit counts, input/output byte totals, successful uploads and manifest hash; reconcile these against R2 operation counters after each build. Do not download the world into this VM workspace.

Implementation estimate: 1,200–1,800 production lines across packer, manifest reader, page store, renderer and integration; 500–800 test/harness lines. Approximately 8–12 engineering days plus 3–5 days of phone/visual validation, assuming existing tile inventory access. This is a new loading/rendering path, not a one-afternoon tuning patch. First instrumented target experiment is 1–2 days; asset pilot and GPU path another 3–5. No new image generation or source harvesting is required.

## 6. Proof plan and advance pass bars

### Measurements

Add a bounded trace ring (20,000 events, explicit export; off by default) with monotonic time, round token, camera pose, viewport/DPR, provider version, window/page/source key and reason. Capture: input start/end; target/current camera; pick start/end/rejections; enqueue/dispatch/header/body completion and bytes; cache tier; HTTP code; bundle success/failure/member timings; decode start/end; upload submit; first drawn frame; native-source coverage; mip/fade; abort reason and bytes wasted; breaker; texture allocation/eviction/context loss. Keep diagnostic target coordinates out of production analytics.

For current-path baseline instrument `window.__tileRound2Log` beyond start/abort; include bundle and Daily pools, otherwise totals lie. Add worker Server-Timing for assembly/cache/member tail, and timing exposure on own host. In Safari cross-origin Resource Timing may be limited; combine instrumented fetch duration with server logs and externally captured network trace rather than treating zero-sized entries as cache hits. CPU copy duration is not GPU completion. Use disjoint timer queries where available and screen video + frame timestamps everywhere; do not use blocking `gl.finish` in the normal timing run.

Define final useful coverage against the versioned manifest at the **final camera pose**. Measure native z9 where present and designated fallback elsewhere; report both fractions. “Tsharp” is the first presented frame with ≥99% available intended imagery coverage and no visible quality regression for the next 500 ms, with any introduction fade finished. Record central 50% and full-view Tsharp separately. Keep camera-settle latency separate from imagery readiness. In ocean, score immediate stable fallback, not impossible native z9. Have the owner compare locked-pose crops to reference tiles: network readiness alone cannot certify visual sharpness.

Reference device: the owner's actual iPhone, recording model, iOS/Safari version, DPR, viewport, battery/thermal state and actual display rate. Additional tests: an older supported iPhone with less memory, a midrange Android Chrome device, and hardware-rendered desktop Chromium for automation. Software-rendered headless is only for request/state correctness, never absolute performance acceptance.

Network profiles: (A) ordinary Wi-Fi with measured RTT/throughput, (B) controlled 50 ms RTT / 10 Mbit/s down / 1 Mbit/s up, (C) 100 ms / 2 Mbit/s constrained mobile. Test cold browser+SW, warm SW/cold GPU, and resident GPU separately; distinguish CDN HIT/MISS rather than forcing random URL keys into normal traffic. Edge-cold tests are a separate staging prefix/sample and their impact is reported.

Sites: Tokyo, Madrid inside pilot, a pilot boundary, Congo, Great Lakes, atoll, ordinary no-z10 land, z9 holes, open ocean, antimeridian, high latitude, and portrait/landscape. Replay home→spin→deep pinch and direct pinned-camera deep jump; zoom reversal, small pan, 90-degree off-target pan, repeated revisit, round change during fetch, background/foreground and context loss. Run 30 paired baseline/new repetitions per principal site/profile on the reference phone, interleave order, and report medians/p95 and sample counts rather than only the fastest run. Boundary cases need at least five functional repeats each.

### Pass/fail gates decided before building

1. **Prepared target:** after five seconds clue dwell on profile B with complete preparation, p95 last-input-to-Tsharp ≤100 ms, median ≤50 ms; zero post-input fetch/decode/upload required for that footprint. ≥95% of reference-phone rounds whose full footprint fits the caps finish preparation within those five seconds. Count non-ready rounds as preparation failures, not exclude them from headline success.
2. **Whole experience:** across the same five-second-dwell cohort, including incomplete preparation, p95 last-input-to-Tsharp ≤300 ms. Compare side-by-side with MapTap at matched ground scale where possible; “MapTap class” requires owner approval and no captured blurry transition during prepared zoom, not just a favorable counter.
3. **Immediate cold jump:** profile B p95 first-input-to-Tsharp ≤3 s and ≥50% lower than paired baseline; report actual bytes. A 2.81 MiB footprint needs ~2.36 s of ideal transfer at 10 Mbit/s before overhead, so this is demanding. Profile C is not promised instant: p95 no worse than baseline, stable fallback immediately, no unbounded retries. Failure here exposes excessive page overfetch.
4. **Motion:** reference phone p95 frame interval ≤20 ms at 60 Hz during gesture and no upload-attributable frame >50 ms; no context loss in a 20-minute mixed-round/pan run. Track thermal degradation, not just first-minute results.
5. **Budget:** never exceed 64 MiB page texture allocation or 8 MiB compressed LRU; speculative ≤3 MiB/round and zero with Save Data. In the representative five-round set, median unused speculative bytes ≤1 MiB/round and measured full-round imagery bytes ≤2× the paired baseline. If this fails, page design does not ship simply because warmed clips look good.
6. **Coverage/visual:** no requests for manifest-known absent tiles; no z10 blocking z9; correct dateline wrapping, no holes/seams/color changes in fixed-pose reference comparisons; preserve stylized globe and ocean transition. Ocean reaches declared terminal coverage within one rendered frame when base is ready. A deliberately missing page falls back without permanent loading.
7. **Cache/reuse:** a one-tile pan retains every overlapping resident page; repeated fully resident deep zoom causes zero imagery network, decode and upload. Cold response can fail independently without invalidating healthy neighbors.

The first prototype must compare three arms: current behavior, never-paused full-ladder compressed prefetch, and direct final-page GPU preparation. This distinguishes anticipation alone from persistent rendering. If the simpler arm meets all gates including bytes and phone jank, document that result and stop expansion for review; do not assume the more invasive design won. No speed claims are considered verified by this design-only deliverable.

## 8. Limits and final recommendation

The strongest established finding is architectural dependency and repeated work, not a proven numerical ranking of network versus GPU on iPhone. The biggest implementation risk is replacing many small resources with pages that waste bytes or cause larger upload stalls; the biggest product limitation is that a player may explore far from the known answer. The design explicitly measures both and does not count prefetch success only among players who happen to use it.

Proceed first with instrumented baseline and a small final-page residency pilot. Do not invest in broader z10 coverage to solve this problem: it adds smoother samples from the same source, not new detail. The durable goal is that the zoom gesture changes how already prepared imagery is sampled, while geography—not transient camera windows—owns resource lifetime.
